# Технические решения

## Применение по карточкам

Требования этого документа вводятся по мере выполнения docs/TASKS.md. Не создавать всю структуру, проверки, ассеты и сборки в одной задаче. T00 работает только с документами; T01 готовит минимальный запуск. Templates и экспорт относятся к T20; проверка сохранения мира к T16. Существующее окружение и готовые команды переиспользуются.

## Движок и структура

Используй Godot 4.7.2 stable, стандартную сборку без .NET, GDScript с типами, Compatibility renderer. Версию бинарника и export templates зафиксируй отдельно. Не используй dev/RC. Если указанная версия объективно недоступна в среде, проверь официальные стабильные релизы, выбери совместимую 4.x и запиши причину, фактическую версию и необходимые изменения команд.

Проект должен открываться обычным Godot Editor. Никакого обязательного внешнего сервера, закрытого плагина, API ключа или установленного Python для запуска самой игры.

Предлагаемая структура, которую можно упростить:
- project.godot и export_presets.cfg.
- scenes/: меню, квартал, персонажи, контейнеры, UI.
- scripts/: player, combat, ai, inventory, crime, economy, quest, save.
- data/: предметы, торговцы, параметры, диалоги.
- assets/: tiles, characters, ui, audio, fonts.
- tools/: установка движка при необходимости, проверки, экспорт, создание ассетов при использовании генератора.
- tests/: независимые игровые сценарии.
- docs/: дизайн, проверки, этапы, фактическое состояние.
- artifacts/: результаты проверок, настоящие скриншоты и сборки; крупные бинарники не коммить без необходимости.

Это ориентир структуры, а не требование создать абстракцию на каждый каталог. Игровой проект в пустом репозитории размещай в корне.

## Границы ответственности

Player обрабатывает ввод и движение. Combat разрешает попадания. Guard AI управляет состояниями и использует общую проверку видимости. Crime принимает событие преступления и определяет действительных свидетелей. Inventory и Economy выполняют операции с предметами и деньгами. Quest проверяет явные события и выдаёт награду. Save сериализует состояние.

UI отображает данные и вызывает игровые операции. Не разрешай GUI напрямую дописывать деньги или обходить правила предметов. Доступность действия определяется той же логикой, которая выполняет действие.

Используй сигналы для конкретных событий, когда это помогает. Не строй универсальную event bus и ECS ради маленького проекта. Общие singleton нужны только для действительно глобального состояния, например управления сохранением и переходами.

## Данные и ID

У мира, NPC, торговцев, контейнеров и квестовых предметов есть стабильные строковые ID. Проверяй их уникальность и корректность ссылок.

Данные предмета: ID, название, описание, базовая цена, тип, возможность продажи/использования, иконка. Экземпляр/стек дополнительно содержит количество и происхождение: честный/краденый, владелец/источник. Для уникальной лампы отдельный стабильный ID экземпляра.

Не сохраняй Godot Object и случайные Runtime Instance ID. Формат сохранения должен быть обычными данными с номером версии. Не разбрасывай игровые значения в разных скриптах.

## Сохранение и восстановление

Пиши в отдельный временный файл, проверяй результат и затем заменяй основное сохранение безопасным способом. Предыдущее корректное сохранение не должно уничтожаться при ошибке записи. Храни резервную копию или иной простой способ восстановления.

Чтение включает проверку версии, типов, необходимых ID и диапазонов. Отсутствующий save разрешает новую игру. Повреждённый save выводит понятную ошибку и предлагает корректную резервную копию, если она существует. Не заменяй молча повреждённый прогресс новой игрой.

Тесты работают в отдельной временной директории и никогда не перезаписывают пользовательский save. Первый этап поддерживает свою версию формата; универсальная система миграций не нужна.

## Ассеты

Одна согласованная стилистика важнее количества декора. Можно использовать бесплатный совместимый набор или нарисовать исходные пиксельные PNG программно. При программной генерации приложи исходник генератора и уже готовые PNG, чтобы игра запускалась без генератора.

Если в среде есть инструмент генерации изображений, его можно применять к ассетам, но наличие инструмента не предполагается. Не создавай зависимость запуска от генеративного сервиса. Генерированное изображение должно пройти ручную/доступную визуальную проверку, обрезку по сетке и согласование палитры.

Укажи происхождение и лицензию сторонних ассетов в assets/ATTRIBUTION.md. Собственные изображения пометь как созданные для проекта. Не объявляй собственными чужие ассеты и не выдумывай лицензии.

Шрифт должен поддерживать кириллицу. Если готового растрового шрифта нет, используй свободный подходящий шрифт и аккуратный размер без потери читаемости. Не притворяйся, что ломаная кириллица соответствует требованиям.

## Облачная среда и воспроизводимость

Сначала проверь содержимое репозитория, инструкции, доступные команды, фактическую версию Godot, наличие рендера и сети. Не предполагается, что в контейнере уже есть движок, GUI или экспортные шаблоны.

Если Godot отсутствует и скачивание разрешено, подготовь воспроизводимый bootstrap для официальной стандартной сборки. Зафиксируй версию, ссылку/источник и проверку целостности, когда доступна официальная контрольная сумма. Не выдумывай хеши. При отсутствии сети опиши точный шаг настройки окружения и продолжай работу, которую можно сделать.

Не полагайся на переменную, экспортированную только внутри отдельного setup shell. Скрипты должны сами находить GODOT_BIN или установленный бинарник. GODOT_BIN является необязательным явным переопределением, а не обязательным секретом.

Обеспечь короткие команды:
1. tools/check.sh: версия, импорт ресурсов, отсутствие ошибок загрузки/скриптов, корректность данных.
2. tools/test.sh: существенные сценарии логики, ненулевой код при провале.
3. tools/export.sh: сборка при наличии совместимых export templates.

Названия можно адаптировать под существующие соглашения репозитория. Все команды и предварительные требования опиши в README.

Для импорта можно использовать Godot --headless --path . --import. Проверь доступные параметры через --help, особенно перед записью видео и экспортом. Команда --test самого движка не заменяет тесты проекта. Подойдёт собственный тестовый SceneTree runner или лёгкий совместимый test framework, если его установка оправдана.

Добавь ограничение времени для автоматических сценариев. Проверяй script errors, отсутствующие ресурсы и вывод ожиданий; одного exit code импорта недостаточно. Не превращай любой WARN из движка в автоматический провал без разбора причины.

## Рендер, сборки и проверка изображения

Headless достаточно для логики. Для настоящего изображения нужен доступный renderer. Если окружение позволяет, используй виртуальный дисплей и программный рендер или другой поддерживаемый способ, запускай настоящий проект и снимай кадры. Наличие Xvfb/Mesa не предполагается. Не создавай «скриншоты» из отдельно нарисованного макета.

Подготовь Linux сборку для доступной среды и Windows x86_64 сборку для пользователя, если установлены нужные export templates. Экспорт Windows из Linux подтверждает создание пакета, а не его запуск на Windows. В README отдельно укажи, что проверено.

Если экспорт недоступен, исходный проект должен оставаться пригодным для открытия в Godot; точно перечисли недостающие зависимости и непроверенные пункты. Не называй такой результат готовой проверенной сборкой.

Для ревью подготовь понятный путь от меню до первого задания. Дополнительный режим review-demo допустим: он задаёт фиксированный начальный мир и выполняет действия через те же игровые команды. Он не должен подменять логику торговли, краж или квестов прямой записью результата.

## Независимость от внешних сервисов

Нужен обычный локальный игровой клиент. Во время игры не выполняй сетевые запросы. В тестах не используй внешние сервисы. Настройки должны быть локальными. Web export необязателен и не должен задерживать основной результат.
